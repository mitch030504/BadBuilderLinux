# Decision: v2.4.1 safety hardening

Date: 2026-11-08
Agent: OpenCode (DeepSeek V4.1 Flash)
Status: accepted

## Context
A full repository audit found 12 issues, including four disk-safety defects: protected Linux disks could still be offered, Windows lost disk identity after formatting, oversized files and directory allocation could pass preflight, and launch configuration could fail after erasure. The release needed to fix these without weakening existing collision, checksum, or privilege boundaries.

## Decision
- Treat all predictable validation and configuration work as preflight: staged entry points, `launch.ini`, FAT32 capacity, FATX paths, and file-size limits must finish before the destructive confirmation.
- Mirror the pinned DiscUtils FAT32 formatter layout exactly, including uncapped partition-allocation cylinders, cluster-size thresholds, FAT size, and directory-entry clusters.
- Persist failed Linux cleanup targets and retry through the existing authenticated helper lease; accept a missing `/run` lease as complete only when the expected mount is gone.
- Route failed downloads and invalid cached archives through the same verified local-archive fallback, with one linked deadline covering headers, body reads, and metadata.
- Revalidate Windows disk identity after formatting and require exactly one FAT32 `BADUPDATE` volume before accepting a drive letter.
- Keep destructive work gated by complete preflight, exact device-path confirmation, identity revalidation, and post-format verification.

## Rationale
Predictable failures must not leave an erased USB or target an unselected disk. Reusing the formatter's own layout avoids false capacity decisions. Persisting cleanup state preserves the helper's lease authentication while giving the user an in-app recovery route. Local fallback keeps documented offline workflows usable without bypassing checksum or approval rules.

## Alternatives Considered
- Keep launch.ini updates post-copy — rejected: a predictable encoding failure would still strand an erased USB.
- Estimate capacity from logical bytes plus a fixed margin — rejected: empty directories and cluster allocation can exceed the disk while logical bytes fit.
- Clear failed cleanup records automatically — rejected: it could allow a new operation while the old mount/lease still exists.
- Fall back to any local archive without verification — rejected: it would bypass the existing trusted-hash and approval model.

## Consequences
- Preflight is stricter and may reject plans that previously passed but would fail during copy.
- Large FAT32 layouts now match DiscUtils across supported sizes; the automated layout check covers 1–16 GiB to stay within Windows runner disk capacity.
- Cleanup recovery depends on the persisted record and the helper lease; manual intervention may still be required if a mount remains busy.
- Physical USB, Windows runtime, and privileged cleanup behavior remain manual validation areas.
